1. 系统定位与目标

本平台是一个面向数学建模竞赛（CUMCM / MCM·ICM）的一体化工作流引擎。它把竞赛解题过程拆解为可编排、可审批、可复现的标准阶段，让 AI 与人类协作者按统一契约完成「题目解析 → 模型选型 → 数据处理 → 模型求解 → 可视化 → 验证 → 论文生成」的完整链路。

核心原则：main.py 是薄编排层——它只负责流程控制、缓存、审批与状态管理；所有真实业务逻辑都在 modules/ 的各子包与 factories/ 求解器中实现。这一分层使平台易于扩展与测试。

2. 总体架构（分层）

系统自顶向下分为 5 层，外加配置与持久化侧翼。每一层只依赖其下层，调用通过「延迟导入」与「反射分发」解耦。

3. 七阶段流水线 & 多分支执行路径

STAGES 定义了 7 个标准阶段。真正执行哪几个阶段，由 run_all() 根据前置分析得出的题目类型查 EXECUTION_PATHS 动态决定——这是「智能问题分析模式」的关键：不同题型走不同分支。

EXECUTION_PATHS 分支

  • optimization：数据处理 → 求解 → 验证 → 论文
  • prediction / classification / simulation / comprehensive：数据处理 → 求解 → 可视化 → 验证 → 论文

run_all 控制节奏

  • 先跑①并请用户确认分析结果；
  • 再跑②并请用户确认模型选择；
  • 随后按分支逐个阶段，每步提示 y/n/q（可视化走交互式入口）。

4. 控制流：run_stage 的内部逻辑

每个阶段都通过 run_stage(stage) 统一调度，内部流程固定且可审计：

  1. 缓存命中：若未禁用缓存且存在 stage_{stage} 缓存且未强制刷新，直接返回缓存结果（WorkflowCache）。
  2. 审批登记：调用 approval_manager.register_operation(...)，风险等级默认 medium，来源标记 AI。
  3. 请求审批：request_approval(op) 按风险/模式决策（见 §6）；未获批准则抛 PermissionError，阶段不执行。
  4. 反射分发：通过 getattr(self, f"_run_{stage}")(**kwargs) 调用对应的薄包装方法，再委托到 modules/NN_xxx_runner.run_xxx（延迟导入）。
  5. 结果落盘：成功后写入缓存、更新 state["stages"][stage]=completed 并 _save_state()，审批日志标记 executed。
  6. 失败处理：异常时 state 标记 failed、审批日志标记 failed 并重新抛出，由 run_all 决定是否继续。
# main.py 中典型的阶段薄包装（延迟导入，保持 main.py 轻量）
def _run_model_solving(self, **kwargs) -> Dict:
    from modules.model_solving_runner import run_model_solving
    return run_model_solving(self, **kwargs)

# run_stage 核心片段
operation = self.approval_manager.register_operation(
    operation_id=f"stage_{stage}_...", operation_type="stage_execution",
    description=f"执行{self._STAGE_NAMES.get(stage, stage)}阶段",
    risk_level="medium", command=f"workflow.run_stage('{stage}')", source="AI")
if not self.approval_manager.request_approval(operation):
    raise PermissionError(f"阶段 {stage} 未获人工批准，无法执行")
result = getattr(self, f"_run_{stage}")(**kwargs)   # 反射调用

5. 模型求解调度机制

model_solving 阶段把「所选模型 + 参数」交给 ModelFactory 统一调度。调度链彻底解耦了「模型名字」与「求解实现」：

统一数据入口

_base.py 提供 _get_xy / _get_x / load_features：既支持直接传 X/y，也支持 data_path 读 CSV，所有求解器共用，避免重复解析。

别名兼容

CATALOG_ALIASES 把「线性回归 / SVM / 灰色预测 / LSTM …」等中文/同义词映射到模型 id，LLM 或用户可用自然语言调用。

工具 Schema

get_tool_schemas() 为每个模型生成 OpenAI function-calling 风格的 solve_<id> schema，供 LLM Agent / MCP 暴露为可调用工具。

6. 人工审批与风险门禁

ApprovalManager 是平台的安全闸门。每个阶段/操作都要先登记再审批，且默认失败闭合（fail-closed）：交互模式下若读取输入失败（EOF），按「拒绝」处理，绝不悄悄放行。

风险等级约定

  • low 任何模式自动批准（approved_by=System）
  • medium 非交互模式自动批准（NonInteractive）；交互模式需人工确认
  • high 同 medium 逻辑，需经回调或人工

request_approval 决策优先级

  1. 非交互模式 → auto_approved_non_interactive
  2. 风险 low → auto_approved(System)
  3. 已注入同步回调 → 由回调返回值决定
  4. 已注入异步回调 → 退化为同步调用
  5. 默认 → 交互提示（EOF 即拒绝）
审批可审计：每次决策写入 logs/approval_log.json，并通过 get_approval_summary() 汇总（总操作数 / 已批准 / 已拒绝 / 已执行 / 批准率）。这满足了「AI 自主操作需可回溯」的合规要求。

状态机：pending → (批准) auto_approved / approved / Callback / AsyncCallback → executed｜(拒绝) rejected。阶段运行器在审批通过后会把 operation["status"] 改为 executed 或 failed。

7. 智能层：LLM Agent 与 MCP Server

LLM Agent（modules/llm_agent）

支持三种决策模式，按 LLM 可用性自动降级：

  • pure_llm：直接由大模型决策；
  • hybrid：LLM 规划 + 真实工具调用求解；
  • rule_fallback：LLM 不可用时退化为规则/启发式。

内置 ReflectionEngine（规则评分，失败调用强制低分、不伪造高分）。依赖模块采用「优先真实模块 + 缺失兜底」的受保护导入，确保评分环境调用真实求解。

MCP Server（modules/mcp_server）

基于标准库 http.server（零第三方依赖），同时提供 REST 与 JSON-RPC 2.0 两种协议：

  • GET /health · GET /tools · POST /tools/<name>/call（真实求解）
  • POST /mcp：tools/list · tools/call · status · summary · approval/respond
  • POST /approve：配合异步审批回调

工具 Schema 直接来自 ModelFactory.get_tool_schemas()；可选 api_key 通过 Authorization: Bearer 或查询参数鉴权。

智能层与求解内核通过同一套 ModelFactory 对接，因此无论是 CLI、LLM Agent 还是 MCP 客户端，调用的都是同一批真实求解器，结果一致、可复现。

8. 配置驱动（workflow_config.yaml）

几乎所有「魔法数字」与策略都外置到 config/workflow_config.yaml（v3.4.2，209 行），实现「改配置不改代码」：

modules

各阶段开关与参数：缺失值/异常值处理策略、缩放方式、CV 折数、可视化样式与尺寸、验证阈值、论文模板与自动生成章节。

limits

提取上限（变量/约束/子问题/关键词）、难度评分信号阈值、AHP 一致性 CR 阈值等——消除散落的 magic number。

output / version_control / progress

论文/图表格式与 DPI；auto_commit 与提交消息格式；state / progress 文件路径。

例如模型求解默认参数（ridge_alpha、kmeans_n_clusters、arima_order …）集中声明；数据处理的质量评分权重（缺失 0.5 / 重复 0.3 / 常量 0.2）也在配置中，便于按赛题调整。

9. 数据契约与产物流转

各阶段通过文件与状态对象交接，形成清晰的产物链：

  • state：workflow_state.json 记录当前阶段与每阶段状态，断点可续。
  • results：各阶段产出结构化 JSON（如 model_solving_result），供下游阶段与论文生成消费。
  • cache：WorkflowCache 缓存阶段结果，支持 --no-cache 强制重算与 --clear-cache 清空。
  • paper / figures：论文 .docx（基于 cumcm_template.docx）与图表 .png/.svg 落地。

10. 关键设计原则

薄编排 + 延迟导入

main.py 只管流程；_run_{stage} 用延迟 import 调用 runner，启动快、依赖解耦。

反射分发

getattr(self, f"_run_{stage}") 用执行路径表替代硬编码 if-elif，新增阶段零侵入。

失败闭合审批

审批默认拒绝，人工/回调确认才放行；全部写入可审计日志。

真实求解不伪造

未实现模型显式报错，ReflectionEngine 失败必扣分，结果可复现可追溯。

配置化消除魔法数

阈值、权重、难度信号等外置 YAML，调参不必改代码。

统一模型契约

别名兼容中文调用、统一数据入口、统一结果结构，CLI/LLM/MCP 共享内核。

一句话总结工作逻辑：「题目类型决定执行分支 → 每阶段先缓存/审批再反射分发 → ModelFactory 按别名+类别把模型名映射到真实求解器 → 结果落盘并进入论文生成，全程可审批、可缓存、可复现。」
