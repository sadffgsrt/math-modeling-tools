# 代码审查标准（CODE REVIEW STANDARD）

适用仓库：`agent/`（数学建模工作流平台，Python 主工程）
生效版本：v3.4.2 起

## 0. 总则与辩证立场

标准的目标是让代码"可维护、可信赖、可演进"，不为合规而合规。本项目的代码质量目前参差不齐，审查标准的首要任务是**收敛系统性风险**（错误被吞、逻辑无测试、密钥外泄），而不是在格式细节上纠缠。

辩证地看，以下张力客观存在，审查时需情境化判断：

- 覆盖率门槛不是越高越好。高覆盖不等于高质量，但本项目核心套件仅 41.5% 覆盖，明显不足，应以渐进方式抬升，而非一步到位卡死主干。
- 宽异常捕获不能一刀切禁止。数学建模中的外部求解器、数据解析、文件 IO 天然容易抛异常，应区分"可预期异常"（应具体捕获并日志）与"未知异常"（应上抛或至少记录堆栈）。
- 门禁硬化要分阶段。一次性把 CI 全量 + 严格门槛打开，会阻塞现有 100 个历史任务的遗留改动，应先修配置错配，再逐步收紧。

## 1. 严重级别定义

| 级别 | 含义 | 合入要求 |
| --- | --- | --- |
| Blocker | 安全漏洞、密钥/隐私外泄、必然导致数据错误、直接破坏 CI | 必须修复，禁止带过 |
| Critical | 核心建模/求解逻辑错误、数值正确性风险、并发/资源泄漏 | 必须修复 |
| Major | 明显设计缺陷、重复代码、缺关键测试、破坏可观测性 | 必须修复或书面记录例外 |
| Minor | 风格、可读性、小性能、日志缺失 | 建议修复 |
| Nit | 命名、注释、空白 | 可选，不阻塞 |

标签写法：评论首行用 `[Blocker]` `[Critical]` `[Major]` `[Minor]` `[Nit]` 标注，便于检索与统计。

## 2. 检查清单

### 2.1 通用（跨语言适用）

- 单一职责：函数/类只做一件事；函数超过 80 行需说明。
- 圈复杂度：单函数分支过多（>15）应拆分。
- 错误处理：见 2.3 本项目特例。
- 可观测性：关键路径有日志，禁止静默失败。
- 项目铁律（来自用户约定）：禁止硬编码与凭空捏造无计算依据的数据；调用数据必须有来源与公式。

### 2.2 Python 专项

- 类型注解：公共函数/方法应有参数与返回类型标注。
- 可变默认参数：禁止 `def f(x=[])`，改用 `x=None` 内部初始化。
- 模块导出：包级公共 API 用 `__all__` 显式声明。
- 异常粒度：捕获具体异常类型，不要 `except Exception` 后无日志。
- 资源管理：`open()`/网络连接用 `with` 或显式关闭。

### 2.3 本项目高风险区（基于 2026-07-27 实测扫描）

实测基线：120 个 `.py` 文件 / 23,750 行；`except Exception` 83 处；裸 `print()` 122 处；`# noqa`/`# type: ignore` 32 处；巨石文件 validator 1201 行、agent 857 行、writer 737 行、main 626 行、web_ui/server 613 行、visualizer 573 行、processor 529 行。

针对这些区域，审查时重点看：

- **错误处理**：`except Exception` 必须伴随日志记录与有意义的回退；禁止裸 `except:`。数学建模外部求解器（scipy/pulp/networkx 等）的异常应具体捕获。
- **日志规范**：禁止裸 `print()` 走项目自带 logger（`modules/utils/logger` 或标准 logging）；CLI 入口允许的 `print` 需注明。
- **类型绕过**：`# noqa` / `# type: ignore` 必须附带原因注释，且不能用于掩盖真实类型错误。
- **巨石文件**：单文件超过 600 行应评估拆分（如 validator 的各类校验器、agent 的各阶段编排）。新代码禁止制造新的巨石文件。
- **门面与单一真相**：跨模块调用走 `modules/__init__.py` 聚合门面与 `stage_planner.plan()`，禁止在多处散落阶段顺序硬编码。

### 2.4 安全（本项目最高优先级）

- 凭证管理：禁止明文 API Key/Token/密码出现在代码或提交中；优先从环境变量或本地 `.env`（不入库）读取。
- 数据边界：用户数据不序列化到日志，不外传到未声明端点。
- 网络外联：任何对外请求需显式且可配置，禁止隐藏通道。
- 敏感信息出现时：若审查发现明文密钥，标记为 `[Blocker]` 并要求改用本地配置，不得合入。

### 2.5 测试质量

- 覆盖率：新代码关联的模块覆盖率不得低于当前套件水平（41.5%），目标渐进到 60%。
- 禁止伪造：测试不得用编造数据"刷过"；数值结果需有独立计算依据或已知基准。
- 测试守卫：依赖可选包（matplotlib/networkx/pulp 等）的测试用 `importorskip` 守卫；需密钥的测试用 `skipif` 守卫。
- 回归：改动不得让绿测集（test_workflow / test_model_solving / test_validation）由绿转红。

## 3. 评论模板

```
[级别] 文件路径:行号
问题：一句话描述
建议：具体改法（含代码片段更佳）
理由：为什么（关联标准第几节 / 风险）
```

示例：
```
[Critical] modules/model_solving/factories/_optimization.py:142
问题：except Exception 吞掉求解器异常后返回空结果，调用方无法感知失败。
建议：捕获具体异常（如 ValueError from scipy），记录 logger.error 并上抛或返回带 error 字段的结果。
理由：标准 2.3 错误处理；空结果会导致下游误判为"无可行解"。
```

## 4. 反模式与正例（本项目真实案例）

| 反模式 | 现状规模 | 正例 |
| --- | --- | --- |
| 裸 `print()` 调试 | 122 处 | `logger.info("stage=%s done", name)` |
| 宽 `except Exception` 无日志 | 83 处 | `except ValueError as e: logger.error(...); raise` |
| `# noqa` 掩盖问题 | 32 处 | 显式处理或加 `# noqa: F401 原因` 注释 |
| 巨石文件 | 7 个 >500 行 | 按职责拆分小模块 |
| 硬编码阶段顺序 | 多处 | 统一调用 `stage_planner.plan(problem_type)` |

## 5. 辩证补充

- 标准不是枷锁。当某条规则与"交付竞赛紧迫性"冲突时，允许书面记录例外（在 PR 备注与 `对话记录.md` 中说明），但例外不得常态化。
- 审查是协作不是审判。评论给出"为什么"与"怎么改"，让作者能复用到下次。
- 量化基线会随硬化推进而变化，本文件中的数字每季度复核一次，避免标准脱离实际。
